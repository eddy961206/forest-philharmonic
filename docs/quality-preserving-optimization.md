# 화질·음원을 유지한 렌더링 최적화

2026-10-23, 사용자 요청대로 이번 최적화와 브레멘 추가 구현·검증은 **주 에이전트가 직접 수행**했어. 이번 작업에 서브에이전트는 사용하지 않았어. 이전 보고서에 기록된 GPT-6.1 Sol의 검증과는 별도야.

## 변경한 처리

- 단원과 지휘자의 팔·소매·손을 같은 geometry와 **동일한 material 객체**별로 묶어 InstancedMesh로 그려. 털의 sheen, 의상, 그림자, 기존 IK 움직임을 유지해. 원래 메시도 계층에 남겨 클릭 시 단원 식별에 사용해.
- 각 프레임에서 움직인 행렬을 복사하고, 숨긴 단원의 인스턴스는 제외해. 관객·방문자 캐릭터는 이 배치의 대상이 아니야.
- 기존 모바일 Lite 팔은 색이 바뀌었을 때만 색상 버퍼를 다시 전송해. GPU의 Float32 값과 비교해서 반올림 차이로 매번 갱신되는 것을 방지해.
- 이번 최적화는 샘플·악보·음표·동시 발음 수·단원 수·원래 화질 설정·그림자 설정을 줄이지 않아.

기준은 `0cdded794267f7caaebbaad6044ce465f963ab69`, 최적화 코드는 `9375de71d6c7a24ad8b42cdec88649ae0b8ed763`이야. 이후 브레멘 기능은 [별도 기록](bremen-easter-egg.md)에 있어. 아래 전후 수치는 브레멘 추가 전 최적화 코드의 측정값이야.

## 실제 연주 화면 비교

장비는 Apple M4 Mac mini / 32GiB / macOS 26.5.1, Chrome 156.0.8078.47의 실제 창과 Metal GPU야. 기존 검증용 CDP 9224를 사용했고, 해당 브라우저에는 측정할 앱 탭 하나만 남겼어. 다른 사용자 앱·시스템 부하는 통제하지 않았어.

홀은 위풍당당 전곡 280초, 스피어는 발퀴레 277초에서 탐색한 뒤 5초 준비하고 20초씩 측정했어. 실제 음원과 단원 애니메이션을 계속 실행했어. 화질 high, renderScale 1, 렌더 DPR 1이야. 관객·그림자·중계·후처리도 실행했어. 카메라는 `[0,16.42,5.9]`, 시선 `[0,2,-9]`, FOV 52야.

### 같은 문서에서 원래 메시와 배치를 번갈아 실행

페이지 재로딩의 큰 편차를 분리하기 위해 같은 실행 문서에서 원래 메시 경로와 배치 경로를 전환했어. 원래 경로에서는 배치를 숨기고 기존 전체 화질 경로처럼 syncLite를 no-op으로 했어. 배치 경로에서는 원래 팔을 숨기고 인스턴스 행렬 동기화를 실행했어. 실제 앱을 다시 빌드한 두 버전의 비교와는 구분해야 해.

최초 A/B 두 번은 준비 실행으로 남기고, 다음 **A/B/B/A 네 번**을 집계했어. 각 실행의 평균에 같은 가중치를 줬어. 중계 카메라도 첫 위치에 고정했어. 단원·조명·음표·오디오·후처리는 정상 실행했어. 이 실험의 실제 viewport는 1200×1189 CSS px야. Puppeteer의 준비 연결이 끊기며 1200×800 에뮬레이션이 해제된 뒤의 크기를 따로 기록했어.

| 측정 지표 | 홀 원래 → 배치 | 스피어 원래 → 배치 |
|---|---:|---:|
| 프레임당 그리기 호출 평균 | 2,791.71 → 2,186.72 (**21.67% 감소**) | 1,043.56 → 873.36 (**16.31% 감소**) |
| 앱 프레임 처리 벽시계 시간 평균 | 19.68 → 17.74ms (**9.82% 감소**) | 4.95 → 5.08ms (**2.50% 증가**) |
| rAF 간격 평균 | 20.22 → 18.95ms | 16.6805 → 16.6804ms |
| 100ms 초과 지연 음표 예약 | 0 → 0 | 0 → 0 |
| 브라우저 underrun 증가 | 0 → 0 | 0 → 0 |

프레임 처리 시간은 JS 프레임 시작부터 렌더 제출 후까지의 벽시계 시간이야. 동기 드라이버 대기가 포함되며 순수 CPU/GPU 시간은 아니야. rAF 간격도 실제 패널 표시 FPS와 같다고 단정하지 않아. 스피어는 이미 약 60Hz였고 처리 시간 개선은 없었어. 행렬 복사 비용도 있으므로 모든 장면에서 더 빨라진다는 주장은 하지 않아.

### 새 탭을 연 전후 A/B/B/A

기준 서버 8098과 후보 서버 8096으로 새 탭을 만들고 직전 측정 탭을 닫았어. 이 비교는 1200×800, high/scale 1이야. 중계 카메라는 원래 자동 동작을 유지했어. 다음 값은 각 20초 실행의 평균이야.

| 공연장 / 순서 | 기준 A1 | 후보 B1 | 후보 B2 | 기준 A2 |
|---|---:|---:|---:|---:|
| 홀 rAF(ms) | 18.83 | 17.90 | 17.86 | 16.68 |
| 홀 처리 시간(ms) | 17.16 | 13.98 | 14.03 | 6.76 |
| 홀 그리기 호출 | 2,529.86 | 1,975.84 | 1,962.13 | 2,400.94 |
| 스피어 rAF(ms) | 16.6805 | 16.6944 | 16.6945 | 16.7083 |
| 스피어 처리 시간(ms) | 4.53 | 4.73 | 4.68 | 4.63 |

홀 기준 실행의 편차가 컸어. 이 결과로 일반적인 FPS 개선율을 확정하지 않았어. 그리기 호출 감소는 두 방식에서 일관됐어. 모든 새 탭 표본은 pageerror 0, 늦은 예약 0, underrun 증가 0이야.

## 화질과 동작 확인

같은 후보 장면을 정지하고 원래 메시/배치만 전환해서 **600×400 render target**에 그렸어. 무대 전체·단원 근접·무대에서 객석을 향한 시점, 양 공연장 6쌍을 비교했어. 이 비교는 scene 직접 렌더라 화면 후처리는 포함하지 않아. 실제 앱 전체 화면 캡처도 따로 남겼어.

- 홀 근접: 240,000픽셀 중 채널 차이 8/255 초과가 1픽셀. 평균 절대 채널 차이 0.000151/255.
- 스피어 무대: 같은 기준으로 1픽셀. 평균 차이 0.000140/255.
- 나머지 네 시점은 해당 기준 차이 0픽셀. 두 역방향 시점은 완전히 같았어.
- Float32 인스턴스 행렬 경계 차이까지 비트 단위로 같다고 주장하지 않아. 원래·배치 PNG를 모두 저장했어.
- Node 회귀 테스트는 부모 변환·비균일 팔 길이 변화에서 월드 정점 오차 <1e-6, 동일 material·그림자 플래그, 단원 숨김/복원, 클릭 교차점/단원 소유권, 정리를 검사해.

## 모바일 경로

Chrome의 iPhone UA·터치·390×844 CSS px·DPR 2 에뮬레이션에서 기존 low 경로를 사용했어. 앱의 실제 렌더 DPR은 기존 제한인 1.25, scale 1이야. 기준/후보 각각 20초 rAF 평균은 둘 다 16.6805ms였어. 처리 시간은 3.334→3.313ms로, FPS 개선을 입증하는 차이는 아니야. pageerror·늦은 예약·underrun 증가 모두 0이야.

별도 기능 검사에서는 같은 Lite 문서에서 동기화를 120번 호출해 두 색상 버퍼의 version 증가가 `[0,0]`임을 확인했어. 단원을 숨겼다가 되돌려 인덱스가 바뀌는 두 경우에도 색상 배열은 강제 전체 재기록 결과와 같았어. 이 기능 검사 시에는 연결을 다시 하면서 viewport가 데스크톱 크기로 돌아왔어. 모바일 화면 성능 결과와 같은 크기라고 표시하지 않았어.

실제 iPhone/iPad·iOS Safari, 저메모리 기기, 발열 후 장시간 성능은 미검증이야.

## 남은 비용과 제한

- 배치는 개별 팔의 frustum culling을 하지 않아. 가까운 시점에서는 화면 밖의 팔 삼각형이 추가 제출될 수 있어. 원래 geometry를 그대로 그리는 대가와 그리기 호출 감소를 함께 고려해야 해.
- 초기 shader 준비·82곡 전곡·모든 자동 카메라·장시간 수치의 개선은 확인하지 않았어. 초기 탐색 CPU profile은 병목 단서만 제공해. 초기 한 번의 큰 개선값과 같은 탭 navigation 비교는 최종 개선율 근거에서 제외했어.
- 기존 BFCache 문서 보존과 PCM 메모리 비용은 그대로야. 이번 변경을 메모리 누수 해결로 표현하지 않아.
- 내부 오디오 누락 카운터와 자동 렌더는 직접 스피커 청취를 대신하지 않아.

## 증거와 재현

[원시 수치·이미지·프로파일](evidence/quality-preserving-optimization/)과 [계산 결과](evidence/quality-preserving-optimization/summary.json), SHA-256 manifest를 함께 보관했어. `fresh-*`는 실제 기준/후보의 새 탭 비교, `paired-*`는 같은 문서의 경로 비교, `equivalence-*`는 정지 화면 비교야. 두 CPU profile은 탐색 자료야. Node 테스트는 최적화 후 218개, 브레멘 추가 후 222개 통과했어.

전용 브라우저에서만 다음 도구를 사용해야 해. measure는 8096/8098의 직전 검사 탭을 닫아. Node와 Puppeteer Core가 필요하며 `PUPPETEER_PATH`로 설치 경로를 지정할 수 있어. 아래는 저장소에서 실행하는 예시야. 결과는 기본 `work/quality-optimization/`에 저장하고 `QA_OUT`으로 바꿀 수 있어.

```sh
# 기준은 별도 폴더에서 0cdded7의 public/server/server.js/package.json을 준비해 8098로 제공
# 후보 서버가 없을 때만 실행
HOST=127.0.0.1 PORT=8096 npm start
# 별도 터미널
cdp-direct launch --port 9224
APP_PORT=8096 node tools/qa/quality-optimization-measure.mjs candidate hall 20 plain
node tools/qa/quality-optimization-paired.mjs hall
node tools/qa/quality-optimization-visual.mjs hall
APP_PORT=8096 MOBILE=1 node tools/qa/quality-optimization-measure.mjs mobile hall 20 plain
node tools/qa/quality-optimization-mobile-colors.mjs
python3 tools/qa/summarize-quality-optimization.py
npm test
```

Sphere도 venue 인자를 `sphere`로 바꿔 같은 순서로 준비해. paired는 전체 화질 후보 페이지가 필요해. 모든 실험은 순차 실행했어. 저장소 스크립트는 원래 계측기의 의존성·출력 절대경로를 환경변수/상대경로로 정리한 사본이야.
