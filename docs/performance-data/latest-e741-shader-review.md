# 마지막 단계의 추가 셰이더 최적화 후보 검토

2026-10-22, 제품 `6c7817218814f00631089eb2c6f150d68190980f`를 고정한 상태에서 `public/js/scene/dome3d.js`를 읽고 검토했어. GPU·브라우저는 실행하지 않았고 제품 코드를 바꾸지 않았어. 기존 A/B 측정 도중 근거 없이 후보를 바꾸지 않기로 했어.

## Forest: 바닥 앞까지만 cylinder grid 탐색 — 단순 변경 기각

후보는 `tg = -ro.y / rd.y`를 먼저 계산해 `gridCyl(..., min(140.0, tg), ...)`로 호출하는 것이었어. 이상적인 순차 grid traversal에서는 바닥 뒤의 나무 탐색을 생략할 수 있지만, **현재 구현에서는 바닥 앞의 나무도 놓칠 수 있어.**

현재 루프는 현재 cell을 검사한 다음 다음 cell로 이동하고, 이동한 축의 `nx`를 한 cell 길이만큼 증가시킨 뒤 `min(nx.x, nx.y) > smax`이면 끝내. 이 시점의 `min(nx)`는 새 cell의 진입 거리가 아니라 출구 거리야. 따라서 새 cell 안에 탐색 끝점이 있으면 그 cell을 검사하기 전에 멈춰. 기존 140m 경계에도 이 근사가 있지만, 이를 가까운 바닥 거리로 옮기면 눈앞의 나무를 누락할 수 있어.

기존 hash·trunk 배치·DDA 식을 JavaScript Float64로 옮긴 짧은 CPU 모델에서 다음 반례를 확인했어. 이 숫자는 GPU 픽셀이나 GLSL Float32 실행 결과가 아니야. 드라이버별 hash와 반올림 차이를 수치적으로 검증한 것으로 해석하면 안 돼. traversal 자체의 잘못된 종료 위치를 보여 주는 모델 반례야.

| 항목 | 모델 값 |
|---|---|
| `uT` | 0 |
| 카메라 `ro` | `[1.3463535756926346, 1.9, 0]` |
| yaw 변환 뒤 단위 방향 `rd` | `[0.9798713422123461, -0.1, 0.172777755255054]` |
| 바닥 거리 `tg` | 19.0 |
| 기존 140m 탐색의 나무 거리 | 16.606214090356673 |
| 해당 cell | `[3, 0]` |
| 나무 중심 x/z, 반경 | `[18.15890813032297, 2.7474833593782932, 0.5541307330743382]` |
| 기존 검사 cell 수 | 4 |
| 짧은 탐색 검사 cell 수 | 3; 나무 없음 `1e9` 반환 |
| 짧은 탐색 종료 비교 | 새 cell 출구 18.941408987949067 > 수평 한계 18.904761305025772 |

기존 결과는 바닥보다 약 2.39m 앞의 나무를 그리지만 단순 수정 결과는 바닥을 그리게 돼. 올바른 개선에는 마지막 부분 cell까지 검사하는 DDA 경계 수정이 함께 필요하고, 이것은 기존 근사 동작 자체도 바꾸어. 그때는 cell 경계·정확한 축 방향·근접 나무·canopy 전환의 픽셀 검증을 새로 해야 해. 이번 후보에는 넣지 않았어.

## Ocean: 고래 march의 불투명 가림 거리 제한 — 논리적 타당성은 있으나 보류

후보는 고래 루프 끝의 `if (tw > t1)`을 `if (tw > min(t1, t))`로 좁히는 것이었어. 유한한 입력에서 이 제한은 기존 최종 `hit && tw < t` 조건과 일관돼. `ds < 0.03`이면 이미 hit로 끝나고, 그렇지 않은 반복에서만 `tw += ds * 0.9`를 하므로 `tw`는 양의 방향으로 증가해. 한 번 `t`를 넘은 뒤 뒤로 돌아와 앞의 hit를 찾을 수 없어. 엄격한 `>`를 유지하면 기존 `t1` 경계도 그대로야. `min(t1,t)`는 루프 바깥에서 계산해도 돼.

하지만 추가로 절약할 수 있는 광선의 범위는 좁아. 카메라 높이는 5.2~6.8m, 고래 bounding ellipsoid의 높이 범위는 14~20m라서 이를 만나는 광선은 위쪽으로 향해. 해수면은 26m로 ellipsoid 뒤에 있고 바닥은 아래라서 둘 다 새 제한으로 줄일 구간을 만들지 않아. 켈프가 ellipsoid 진입보다 앞이면 기존 `tw < t` 조건이 이미 루프 전체를 생략해. 남는 후보는 ellipsoid에 들어간 뒤 켈프에 가려지는 경우인데, 켈프 최고 높이가 15m라 가능한 높이 겹침도 14~15m뿐이야.

따라서 비싼 SDF 호출을 일부 생략할 수 있는 작은 변경이지만, 현재 소스만으로 전체 픽셀·프레임의 유의미한 절약량을 주장할 수 없어. 실제 GPU 호출 수·픽셀 동일성·시간 측정 없이 후기 변경을 추가할 이유가 약해서 보류했어. 현재 forest/crossfade A/B 결과를 이 미적용 아이디어의 개선 수치로 사용할 수 없어.
