# 최신 main 대비 렌더링 측정 독립 검토

2026-10-22에 읽은 **A/B와 역순 B/A 두 쌍**의 검토야. 최종 보고서와 별개로 각 반복의 방향도 남겼어. 이 검토에서는 GPU·브라우저·이미지 계산을 추가로 실행하지 않았고, JSON과 소스만 읽었어.

- 기준: `e741811d1d7a040afcdd3a8230465980c64f82fc`
- 후보: `6c7817218814f00631089eb2c6f150d68190980f`
- 원본: 측정 디렉터리 `verification/high/render`의 `{baseline,candidate}-{a,b}-full-{hall,sphere}-high-desktop-sync.json` 여덟 파일.
- 환경: Linux x64, Chromium 153.0.8010.0, Playwright 1.62.1, ANGLE SwiftShader, headless, 640×360, DPR 1, high, renderScale 1, full 경로.
- 방법: 실제 `frame()` 호출 뒤 1픽셀 `readPixels`로 완료를 기다렸어. 장면마다 준비 2프레임, 수집 4프레임이야. 일반 RAF FPS, 순수 GPU 시간, 실제 PC·스마트폰 성능은 이 측정에서 구하지 않았어.

## 동일 조건과 데이터 유효성

여덟 파일 모두 `PASS`이고 페이지 오류·console 오류·요청 실패가 없어. 모든 표본에서 context loss와 GL 오류가 없고, 페이지가 visible이며, high와 renderScale 1을 유지했어. `ReadPixels` stall 경고는 이 동기식 측정 방법의 결과야.

두 버전 사이에서 fixture·collector·helper 해시, 환경, 장면 순서, 카메라 위치·목표·FOV, 곡과 음악 시점, 관객 난수 seed, 렌더 설정, 효과 설정이 일치해. Hall은 1,885석 중 1,503명, Sphere는 13,851석 중 11,076명으로 동일해. 실제 오디오 엔진은 생성하지만 음표 스케줄러를 끄고 합성 음악 시계를 사용해. 따라서 이 자료는 오디오 글리치·음질·실제 재생 동기화 검증이 아니야.

각 파일의 수집 전후 `sourceHashes`가 같고, 나열된 12개 URL의 바이트 해시를 해당 Git 커밋의 `public/` 파일과 대조해 모두 일치했어. 기준에 없는 `js/quality.js`의 404는 후보에서 추가된 모듈이라 예상된 상태야. 이 목록은 전체 서버 파일 manifest가 아니므로 모든 의존 파일을 개별 검증했다고 확대해서 말할 수 없어. 관객 소스는 기준과 후보에서 동일해.

Sphere의 5개 장면은 양쪽 모두 돔 `VERIFIED`야. 준비 프레임 중 실제 메인 카메라 draw와 셰이더 ready/link를 확인했다는 뜻이며, 픽셀의 올바른 색이나 화면 품질까지 입증하지는 않아. 최신 e741의 PNG 비교는 별도 결과가 필요해. `recovery-20261022/visual-summary.*`는 과거 1f/dea 자료라 여기에 대신 쓸 수 없어.

Hall front의 삼각형은 약 37.1% 줄었고, broadcast-return은 calls 약 11.1%·삼각형 약 17.2% 감소했어. 반면 wide와 hidden은 제출량이 같아. 특히 hidden의 600 calls는 최신 main도 이미 달성하므로 과거 main 대비 가시성 절약을 최신 기준의 신규 성과로 계산하면 안 돼.

Sphere forest와 crossfade는 매 프레임 정확히 6,588개 삼각형이 줄었어. 이는 갱신한 3개 큐브 면마다 proxy가 2,208 → 12개 삼각형으로 줄어든 값과 맞아. 전체 삼각형의 약 0.22%로, 이 변경만으로 큰 프레임 개선을 주장할 근거는 없어. broadcast는 calls 약 10.8%·삼각형 약 3.0% 감소했지만 나머지 장면은 시간이 혼재해. **이 첫 쌍만으로 Sphere 전반이 더 부드러워졌다고 입증할 수는 없어.**

## 메모리·CPU 지표 해석

Hall의 `performance.memory` 표본은 기준 410,000,000, 후보 386,000,000 byte로 모든 장면에서 같은 버킷 값이야. 하지만 CDP 종료 heap은 wide 23,871,700 → 24,466,160, hidden 23,828,816 → 25,094,876, return 24,297,692 → 25,687,140 byte로 오히려 증가했어. 반대로 front는 감소했어. 동일 GC 지점도 아니므로 지속 메모리 24MB 절감을 확정할 수 없어. Sphere는 양쪽 버킷이 435,000,000 byte로 같고, CDP heap은 후보가 적지만 역시 GC 시점 차이를 분리하지 않았어.

렌더러 geometry 개수는 Hall에서 13~16개, Sphere에서 13개 줄고 texture 개수는 두 공연장에서 1개씩 줄었어. 이 값은 객체 수이며 GPU 메모리 byte나 텍스처 크기 절감률이 아니야. CDP `TaskDuration`에는 동기식 readPixels 대기와 수집기 비용이 섞이므로 CPU 사용률이나 순수 GPU 시간으로 보고하지 않아.

## 소스 차이의 정확성·시각 위험 재검토

- **최신 main 보존:** 관객 코드는 main과 동일해. Sphere 최소 밝기와 Apple GPU의 NaN·검은 화면 수정도 남아 있어. 큐브맵 가시 면 마스크와 두 세계 교대 갱신은 main의 기존 구현이야.
- **Hall 좌석:** 세부 batch를 모두 그리는 시점에만 같은 geometry와 인스턴스의 큰 batch를 선택해. 가까이에서는 화면 밖 공간 batch를 제외해 삼각형을 줄여. `scene.onBeforeRender`는 Three의 render list 생성 전에 실행되어 중계와 메인 카메라가 독립적으로 선택해. 좌석은 castShadow가 꺼져 있어 이 선택이 그림자 caster를 바꾸지 않아. 큰 batch의 별도 instance 데이터와 장면 노드 비용은 생기므로 메모리 무료인 변경은 아니야. 작은 경계·변환·picking 테스트는 이미 있지만 전 좌석과 모든 회전 각도의 화면 검증을 대체하지 않아.
- **그림자 재사용:** 음악가 instance 동기화 뒤 매 프레임 shadow 갱신을 요청하고 첫 장면 render가 만든 shadow map을 두 번째 카메라가 재사용해. 현재 중계 callback은 돔 live texture만 바꾸므로 다른 caster 상태로 그림자를 만드는 차이는 확인되지 않았어. 미래에 카메라별 caster visibility·layers·light를 추가하면 이 가정도 검토해야 해. 중계가 켜지는 순간의 그림자 최신성은 브라우저 회귀 항목이야.
- **돔 순서·proxy:** high는 큐브 크기 640과 매 프레임 정책을 유지하고, medium도 최초 512를 유지해. opaque 건물 뒤에 돔을 그려 가려진 픽셀의 비싼 fragment 작업을 줄이려는 변경이야. 좌석 윤곽·유리·반투명 조명과 crossfade의 실제 픽셀은 별도 비교가 필요해. box proxy의 방향은 수학적으로 같지만 모서리 보간·하드웨어 드라이버 차이는 SwiftShader 이외에서 검증하지 않았어.
- **품질 전환:** 동적 품질에서 큐브 target을 실제로 resize하며 low는 384를 사용해. 이는 고정 high 동일 품질 성과와 분리해야 해. resize 뒤 모든 face를 stale로 표시하는 처리는 있고, 화면 밖 면으로 다시 회전하는 경우는 회귀 검증 항목이야. 모바일 high라도 기존 Lite 경로는 남아 있어 모바일에서 정식 3D 세계를 확보했다고 주장할 수 없어.
- **중계·자막:** 숨겨진 중계가 다시 나타날 때 즉시 새 화면을 찍어. 이는 과거 검은/낡은 화면과의 픽셀 차이를 의도적으로 만들 수 있어. 자막의 fade·slide 값을 반올림하던 main 캐시 대신 정확히 같은 값만 재사용하므로 fade 중 업로드가 조금 늘 수 있지만 정밀도를 보존해. 웹폰트 로딩 후 다시 그리는 처리도 남아 있어. 자막과 일부 shot 시간은 wall clock을 써서 합성 음악 시계가 같아도 모든 애니메이션 픽셀이 자동으로 동일해지는 것은 아니야.

이 검토에서 제품 코드를 추가 수정하지 않았어. 초기 로딩, 실제 자동 품질 정책, 장시간 열·배터리·메모리 안정성, iOS/Android 실기기, 실제 음향은 이 8개 JSON의 범위 밖이야.
